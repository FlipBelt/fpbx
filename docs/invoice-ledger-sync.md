# 发票自动归档同步模块

## 1. 定位与边界

本模块隶属于“发票自动报销助手”，但作为独立项目维护。它只负责审批成功后的发票归档，不重新实现报销主流程，也不改变付款截图金额校验和 OA 审批表单的业务口径。

输入是审批关联附件中的发票 OCR 快照、审批编号和审批发起时间；输出是按月份归档到钉钉发票台账的可审计事件。付款截图、行程单和订单页不进入发票台账发票行。

## 2. 当前基线（2026-09-15）

- 本地 `invoiceLedger.enabled=true`，`mode=audit` 已显式配置。
- 生产 `invoiceLedger.enabled=true`，当前仍为 `mode=audit`；audit 只记录提取、去重和审计结果，不写入钉钉台账。
- 生产 PM2 主服务 `reimbursement-assistant` 和 `reimbursement-scheduled-worker` 均为 `online`，监听端口为 `8793`；根路径健康检查返回 HTTP 200。管理工作台健康接口需要管理员会话，匿名请求返回 401 属于预期行为。
- 生产当前日期对应的 `2026-09` 台账已登记并通过钉钉只读 API 校验：1 个工作表、13 列完整表头、A 列非空 2 行。`2026-05` 模板也可访问且表头一致。
- 生产和本地月份登记均覆盖 `2026-05` 至 `2026-12`，当前月份不依赖五月模板回退。

生产配置核验不得把 `dingtalk.config.json`、环境变量、SSH 私钥或 access token 打印到日志或聊天中。

## 3. 数据契约

台账 A:M 共 13 列，顺序固定为：

| 列 | 字段 |
| --- | --- |
| A | 序号 |
| B | 数电发票号码 |
| C | 销方识别号 |
| D | 销方名称 |
| E | 购方识别号 |
| F | 购买方名称 |
| G | 开票日期 |
| H | 货物或应税劳务名称 |
| I | 金额 |
| J | 税额 |
| K | 价税合计 |
| L | 入账时间 |
| M | 是否入账 |

发票字段快照由 `invoice-ledger-extraction.mjs` 统一生成，并保留字段来源、票种、解析质量和异常信息。铁路客票可以使用票种专用的核心字段规则，但不能用空值填充未知金额或发票标识。

## 4. 处理流程

1. 审批成功后，从持久化 OCR 快照收集发票附件；附件角色先经过发票/付款/其他分流。
2. 由审批发起月份选择目标台账；月度登记由 `data/invoice-ledger-sync.json` 管理。
3. 用发票号码、销方识别号、价税合计和内容指纹做去重；不确定的重复只进入审计/人工处理。
4. 对快照执行字段完整性门槛。解析失败、原件缺失、无 OCR 快照或金额关系不一致时只记录原因，不拼接或猜测字段。
5. `audit` 模式只落审计事件；`sync` 模式才会备份目标范围、写入、回读校验并记录行号。
6. 审批级回滚只在当前行仍与系统写入快照一致，且“是否入账”为空或“否”时自动执行；人工改动或已入账行转人工处理。

关键实现位置：

- `invoice-ledger-extraction.mjs`、`invoice-ledger-pdf-extraction.mjs`：字段解析和 PDF/OCR 回退。
- `invoice-ledger.mjs`：月份、快照和 13 列台账契约。
- `server.mjs`：审批成功触发、同步策略、去重、审计、回滚和管理接口。
- `scripts/invoice-ledger-historical-recovery.mjs`：历史审计、恢复、修复和安全回填。
- `发票台账批量录入工具/`：人工登记月份、预览、补录和回滚入口。

## 5. 历史回填基线与 24 条跳过记录

生产持久化的第三次安全回填任务已完成，结果为：`eligible=82`、`skipped=24`、`duplicate=0`，9 个批次，启用铁路客票规则，并保存了写入前备份。此前确认的 82 条写入必须以回读结果为准。

24 条不能只用“失败”概括，当前可审计记录给出的分类如下：

| 数量 | 证据分类 | 处理要求 |
| ---: | --- | --- |
| 11 | 未形成可写入的结构化发票字段；发票号、销方信息、日期、项目、金额、税额和价税合计等关键字段均缺失 | 补充可读原件或已有 OCR 快照后重新审计；不得人工猜填 |
| 4 | 缺少价税合计 | 补充原件/OCR 并确认总额后再处理 |
| 3 | 缺少销方识别号 | 补充原件/OCR；不能以名称替代税号 |
| 1 | 缺少开票日期 | 补充原件/OCR 后复核月份和去重指纹 |
| 1 | 缺少销方识别号、销方名称和购买方名称 | 补充购销双方信息后再处理 |
| 1 | 缺少销方信息、金额和税额，且金额关系不一致 | 重新取得完整发票字段，确认金额关系 |
| 2 | 缺少金额和税额，且金额关系不一致 | 重新取得完整发票字段，确认金额关系 |
| 1 | 解析器标记为 `ready`，但仍未通过严格台账写入门槛（铁路客票缺少购方识别号） | 由人工确认票种规则和财务字段要求后再决定 |

另有 3 条涉及金额/税额/价税合计关系不一致，已包含在上表相应行中。23 条状态为 `needs_review`，1 条为严格门槛拦截；没有证据支持绕过去重或完整性检查。

当前持久化记录能确认字段缺失和解析质量，但不能把每一条进一步断言为“原件不可读”或“没有 OCR 缓存”。只有补回原件或补齐已有 OCR 快照后，才允许重新处理；不要重复调用付费 OCR。

## 6. 测试与上线门槛

归档模块回归测试：

```bash
npm run test:invoice-ledger-local-parser
npm run test:invoice-ledger
npm run test:invoice-ledger-audit
npm run test:invoice-ledger-sync-policy
npm run test:invoice-ledger-repair
```

本轮迁移后五项均通过。正式开启生产写入前还必须满足：

1. 生产当前模式、PM2 两个进程和健康检查已重新核验。
2. 当前目标月份登记、工作簿权限、13 列表头和回读能力已通过只读检查。
3. 明确获得“从 audit 切换到 sync”的用户确认。
4. 先用可回滚的小批量灰度，写前备份、写后回读、审计事件和行数均一致。
5. 灰度通过后才扩大范围；任何回读不一致、人工修改冲突或关键字段缺失都必须停止并保留证据。

## 7. 生产只读核验参考

连接参数只从 `deploy/服务器部署配置.local.json` 读取。核验时只输出主机、进程名、状态、健康 HTTP 状态、`invoiceLedger.enabled/mode` 和非敏感台账元信息；私钥、配置全文、环境变量全文、token 和实际发票行不得输出。

生产上一轮核验结果：主服务和 scheduled worker 均 `online`，根路径 HTTP 200，生产仍为 `audit`。PM2 版本提示过内存版本与本地版本不一致，但本轮没有执行 `pm2 update` 或重启。
